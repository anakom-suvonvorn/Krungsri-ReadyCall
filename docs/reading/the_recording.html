What Happens to the Caller's Voice

Five things landed in one session. The largest one takes a person's recorded voice and puts it somewhere it can survive a restart without becoming a liability. This page is what each of them actually does, in order, with no jargon that is not explained first.

Written because "the encrypted recording landed" is a sentence that tells you nothing.

The short version

One paragraph each

The recording — a caller who says yes to being recorded now has their audio written to storage, scrambled with a key, with a date on it after which it must be deleted. A caller who says no leaves nothing behind at all. You can check that yourself by counting files.

The empty panel — when the transcript box on the agent's screen is empty, it now says whether that is because the caller was silent or because our speech system broke. It used to be unable to tell you.

The runaway — if the speech model hangs, it is now killed after eight seconds instead of holding up every sentence behind it. That needed the model to be running in its own process, which is why it took a while.

The caller nobody took — your Q31. Fixed exactly as you decided: it circles back forever by default, and the card tells the agent which round it is and whether they are the last person who could take it.

The words are written down — the transcript now survives a restart. Before, it lived only in memory.

Part one

The recording, from a voice to a file

Start with what was already true before this session, because the new part is small and sits on top of it.

When somebody calls, the phone line delivers audio in tiny packets — twenty milliseconds each, which is about the length of a single syllable's beginning. Something has to take those packets, convert them into one standard shape (16,000 numbers per second, one channel), and hand them onward. That thing is the media gateway, and it has existed since the audio work landed a few days ago.

The gateway does not care what is being said. It reshapes and passes on. Whoever wants the audio subscribes, and gets every frame.

Until this week there was exactly one subscriber: the transcriber. Now there are two.

A bug this shape caused, caught before it shipped

The gateway used to replace a leg every time somebody opened one. With one subscriber that never mattered. With two, whoever opened first would silently stop receiving audio while still believing it was subscribed — running, correct, and fed nothing. That exact shape has bitten this project four times before, so it now has two tests that fail if the fix is removed.

The moment consent is checked, and why it is late on purpose

The caller is asked, in Thai, whether they want the pre-call recording. Press 1 for yes, 2 for no. Here is the thing that makes the timing awkward: the audio starts flowing before they answer. That is deliberate — the window while their offer is ringing at an agent's desk is the same window in which they are talking, and losing it would lose the point of the product.

So when do you check consent? If you check when the audio starts, you are too early — the keypress can arrive a second later, and you would have to either throw away everybody whose answer was slow, or record them anyway.

The answer: check at the very end, when the audio is sealed. The frames accumulate in memory the whole time. At the moment the recording closes, the system asks the call session one question: did this person grant the recording consent? If yes, it goes to storage. If no, the buffer is dropped and nothing is written anywhere.

Checked, not asserted

Two calls were placed against a real storage server — one pressing 1, one pressing 2 — and the bucket was listed afterwards. One object. That is the version of a privacy promise you can count rather than read.

What is actually in the file

This is the part worth understanding properly, because "it's encrypted" is not an explanation of anything.

The naive approach is: have one password, scramble every recording with it, keep the password somewhere safe. That works until you want to delete one recording, or rotate the password, or give someone access to one call and not the rest. Then you are re-scrambling everything.

So the standard approach — and what every serious system does — is envelope encryption, which is two locks instead of one.

Think of it as a locked box inside a locked room. The box's key is taped to the outside of the box, but that key is itself inside a smaller locked box, and the only thing that opens that is the room key, which is never in the room.

Why bother, instead of one password for everything?

  • Deleting becomes trivial. Destroy a master key and everything locked under it is unreadable, whether or not the delete job finished. That is what makes a legal deletion promise real rather than aspirational.
  • Rotating becomes possible. Each file records which master locked it, by name. Introduce a new master, and old files still open under the old one.
  • Leaking the database is not leaking the audio. The index of recordings names the master key. It does not contain it, and it does not contain the per-file key either — that lives inside the file.

One piece of cryptography, not four

There are four places a recording could be stored: in memory, in a folder, in MinIO on a laptop, or in Amazon S3. The tempting design is for each of them to encrypt its own files.

That would mean four pieces of cryptography to review — and the one nobody reviewed carefully would be the one holding a real customer. So instead there is exactly one, and it sits in front of all four. Every storage backend receives scrambled bytes and could not read them if it wanted to.

A refusal that was correct, and is now the wrong refusal

Before this session the code deliberately would not write recordings to a folder on disk, and said so: a real recording must never land unencrypted on a dev machine. That was right while nothing encrypted. It is wrong now — what lands in a folder is scrambled bytes with no key beside them, so the property the refusal was protecting is now guaranteed by construction rather than by absence. The old note is a good example of a rule that was correct until the thing it feared stopped being possible.

The one way to get this badly wrong, and the guard against it

If you do not set a master key, the system generates one when it starts up — a different one every time. Combined with in-memory storage that is perfectly coherent: the files die with the process and so does the key.

Combined with real storage it is a disaster of a specific, quiet kind. Every recording would be written successfully. Every one would satisfy an audit. Every one would be permanently unopenable the moment the process restarted, and nobody would find out for months.

So the app refuses to start

Durable storage without a master key is refused at startup, with a message telling you how to generate one. Ciphertext nobody can ever read is worse than an honest gap — at least a gap is visible.

When it is written, and when it is deleted

Not while the agent is picking up

The obvious place to upload the file is the moment the agent presses Accept. That is wrong, and the reason is a rule this project keeps coming back to: the call is never waiting on infrastructure.

Pressing Accept is the instant a human is connected to a distressed person. Putting a network round-trip to a storage server in the middle of that is exactly the wrong place for it. So Accept does something cheap — it hands the buffer to a queue and returns — and the upload happens a moment later on the background sweep that already runs once a second. If the upload fails, it keeps its place and is retried.

There is a test that fails if somebody ever moves the upload back into the accept path. It does not measure timing; it asserts that after Accept the store is still empty and the work is queued. A timing test would just get slower and be ignored.

The row goes in last

There is a table listing every recording: where it is, which master key protects it, how long it is, when it must be deleted. The row is written after the storage server confirms the file, never before.

The other order produces the worst outcome available: a recording that appears in every report, satisfies every audit, and plays nothing.

The deletion date is stamped on the way in

Each recording carries the date after which it must be deleted, calculated when it is stored, from the retention setting as it stood at that moment. Not calculated later.

If you calculated it at deletion time instead, then lowering the retention setting would silently shorten the life of audio already held, and raising it would silently extend it. The promise that binds is the one that was true when the caller said yes.

The deletion job itself is a script you run, not a background task that runs itself. Deletion is the operation you least want happening unattended on a demo machine at 2 a.m. It prints which storage it is about to act on before it does anything, has a dry-run mode, and refuses outright if pointed at in-memory storage — where a clean run would be a green tick over an untouched bucket, which is the most misleading result available.

And it deletes the file before the row. The other order can leave a file with no row pointing at it: audio nobody knows they are holding, invisible to every report.

Part two

The screen now says why it is empty

The agent's screen has a transcript panel. When it is empty it shows a sentence explaining why — and one of those sentences, "ระบบถอดความไม่พร้อมใช้งานในสายนี้" (the transcription system was unavailable on this call), could never appear. The code that decided the reason always answered "no problem", so a caller whose speech model had crashed looked exactly like a caller who had said nothing.

Now the transcriber reports every utterance an engine failure cost, and the layer above — the only one that can see both the transcriber and the caller — decides what to say.

The rule is deliberately narrow. It claims "unavailable" only when the engine failed and nothing at all was transcribed. Here is why that matters: most callers who accept the recording and then wait quietly produce no turns at all. A rule that looked only at "the transcript is empty" would put a system failure on the agent's screen about every single one of them.

And a call where five of six sentences arrived? That is thinner, but saying "the system was unavailable" about it would be a bigger claim than the evidence supports. It is logged loudly and the brief does not lie about it.

Part three

Killing a runaway

Some background. A speech model handed a second of near-silence once took 8.6 seconds and came back with invented Thai. There are three guards against that, and all three are detectors: they catch the bad output after it arrives. By then the time is already spent, and — worse — the transcriber processes one utterance at a time, so everything the caller says next is queued behind the stuck one.

The preventer is a deadline. And a deadline that cannot be enforced is not a deadline.

This was written down months ago as a thing that could not be built, in one of the more useful notes in the decision log:

asyncio.wait_for around to_thread does not kill the thread, so a runaway decode has to be killed with the process. Half-implementing it now would be a guard that looks like one and is not.

In plain terms: in Python you can stop waiting for something, but you cannot make it stop. If the model is chewing on an utterance, telling it "you have run out of time" achieves nothing — it keeps chewing, keeps holding the graphics card, and is still there for the next sentence. The only thing you can actually kill is a whole process.

So the model now runs in its own process. Everything above it is unchanged — the code that asks for a transcription cannot tell the difference, which is the entire point of the way this system is structured.

The test for this does not check that an error was raised. It checks that the process is gone — because a guard that raised an error and left the model running would pass an error test while still holding the graphics card.

This is off by default. Every test, every scripted demo and the stage-safe path run the model in the main process, where a subprocess would buy nothing and cost a spawn. It is for the configuration with a real model in it.

Part four

The caller nobody would take

This is your Q31, and it is the one with a genuinely nasty failure mode.

When an agent declines a call, they are excluded from being offered that same call again — otherwise the matcher would immediately ring them back, which is obviously wrong. That exclusion had no expiry.

So: a caller that every qualified agent declines has no candidates left. Not one. And the safety net that rescues long-waiting callers picks from qualified agents — all of whom are excluded — so it could not help either.

The caller waited for the rest of the shift. No error, no failing test, nothing in a log. The queue showed them as being handled.

Your three decisions, as built

QuestionBuilt
Does a ring-out count as a decline? Yes. And there is a second reason beyond "the caller cannot tell": if it did not count, one agent who walked away from their desk would keep the pool looking un-exhausted forever, and the caller would never get a second round at all.
Is there a cap? A setting, defaulting to no cap. 0 means keep circling. Your reasoning is recorded word-for-word in the decision log, because the argument will outlive the code.
Tell the agent? Yes, with the round number, as you asked. Plus the second message you suggested.

On the "how many agents can take this" question

You proposed always showing a count, then talked yourself out of it. You were right, and there is a rule underneath your instinct worth naming:

The rule

Show a fact when it increases responsibility. Never when it diffuses it.

"Three others could take this" is a diffusion-of-responsibility prompt on a card whose other button is decline — and it is not actionable either. The agent can do nothing with "3"; it is information about the system rather than about this caller.

"You are the only one who can take this" is the opposite on both counts. It is the one thing the agent cannot work out for themselves, and it is the truthful answer to what declining will actually do: the call comes straight back to them.

One more detail worth knowing: "the only one who can take it" is counted from the matcher's own list of candidates, using the exact same filter the matcher used to decide who to ring. Not a second calculation of who is available. Computing availability twice, in two places, is precisely how an earlier bug happened where a caller was offered to an agent whose own screen said they were unavailable.

Part five

The words are written down

The transcript reached the agent's screen last week. It lived only in memory: restart the server and an in-flight transcript was gone.

That was defensible while it matched what a restart already does to the caller's place in the queue. It stopped being defensible the moment the audio became durable — a call whose recording survives and whose words do not is a worse asymmetry than losing both.

Each sentence is now written as it happens, by a fourth subscriber to the same stream — its own, not a line added inside the code that feeds the screen. If it shared, a storage failure could blank the agent's panel. Separated, a failed write costs a database row and nothing else. There is a test that publishes through a storage layer which deliberately explodes, and asserts the screen still received the sentence.

Written per sentence rather than all at once at the end, because the case a durable transcript is for is the call that ends badly. Verified against a real database: six sentences stored for a call nobody accepted.

What this does not do

Being clear about the edges matters more than the list of wins.

  • The key ring is not a real vault. The master key sits in the process environment, which means anyone who can read that environment can read the recordings. Replacing it with a proper vault is a later phase, and it is a second adapter rather than a rewrite — that is why the key ring is a swappable piece rather than code sprinkled around.
  • There is no player. The recording exists and decrypts; nothing offers it to the agent to listen to. That is now a screen job, not a storage one.
  • Only the caller's side is recorded. The agent's half of the conversation is a later phase.
  • The deletion job covers audio and text, and not briefs or snapshots. A full erasure request would still need those.
