What Survives a Restart

Every other part of this system has a screen you can point at. This one runs when nothing is looking, is invisible when it works, and announces itself only by coming back wrong. So here it is, made visible.

25 Aug 2026 9 tables · 441 tests D75 – D79 · B9

01 — the problemA shift lived in a dictionary

Until this phase, everything the contact centre knew about the current moment lived in Python variables. Agents' declared status. Which caller was waiting and how long. Who had already declined a call. What an agent had attested about a caller's identity. All of it in memory, in one process.

Which is fine until the process ends — a deploy, a crash, a laptop going to sleep mid-demo. Then every agent came back silently NOT_READY, whatever they had actually declared, and every call in flight ceased to exist. An agent who had properly excused themselves for lunch was reported for the rest of the day as someone who had gone quiet.

The obvious fix is "add a database". The interesting part is that this turns out to be two separate questions, and only one of them is about SQL: what deserves to be written down, and what should simply be worked out again.

The split is not arbitrary and it is not a limitation to be fixed later. Everything in the right-hand state is something the system genuinely does not know after a restart, and inventing it would be worse than admitting it.

The person's axis survives, because they said it. The platform's axis does not, because after a restart the platform knows nothing.

Agents carry two independent states in this system: what the platform has given them to do (offline, available, on a call, in after-call work) and what they themselves have declared (ready, break, lunch, last call). That distinction was introduced for a different reason entirely — to tell "they chose break" apart from "nobody picked up" in a shift report.

A restart is the first time it had to do real work. Lunch comes back because a person said it. ON_CALL does not, because there is no socket, no offer and no conversation — restoring it would assert a call that is not happening and let the matcher route work to a desk that is not there.

the one exception, and why

READY and LAST_CALL are excluded from the carry-forward even though they are the person's own words. They are the only two values that make the platform send someone a call, and after a restart we cannot know whether that person came back. Everything else — break, lunch, training, admin — is already a way of saying not me, so carrying it forward is safe as well as truthful.

not tables, on purpose

Each of these is computed from a table that already exists. A second copy would be a second thing that can disagree — and the copy is always the one that ends up wrong.

The waiting pool is the clearest case. A queue_entries table would be a second answer to "is this caller waiting?", and the call's own state is already the first. Keep both and they drift; one of them starts lying and nothing notices.

Accrued wait is the one worth dwelling on. It is recomputed from queued_at rather than restored from a counter. So a caller who sat through our outage comes back more urgent, not reset to zero — being pushed down the queue because the server restarted is precisely the outcome the urgency scoring exists to prevent.

04 — the shapeWrite down, read from memory

The instinctive way to add persistence is to have services read from the database. That was rejected, and not for performance folklore. Several of these services are read inside the matcher tick, which runs every second against a 50 ms budget: 

AssignmentService.excluded_agents(call)   ← inside the matcher tick, every second
AttestationService.history(call)          ← on every workstation refresh
DispatchService.waiting()                 ← on every tick

Making those await a query puts a network round trip in the middle of routing a live call, and ripples async through every route that reads. So instead: write through on every change, read from memory, rebuild at startup.

Three things make that honest rather than merely convenient:

  • One writer, one process. The usual reason to read through is that somebody else might have written. Nobody else can.
  • The same choice was already made for presence, with its reasoning written down. Doing it differently for the other five stores would leave two durability models in one codebase — worse than either.
  • There is a stated trigger to revisit it: the moment two processes need to see the same call. At that point the in-memory copy stops being a projection and becomes a cache with an invalidation problem, which wants a different answer entirely.
the tradeoff, stated rather than hidden

If a write fails after the in-memory change, the two disagree for one process lifetime. The next restart corrects it, because the durable record is what gets rebuilt from — never the other way round. That direction is the whole safety property.

05 — the orderWhat restore does, in sequence

The order is the design, not an implementation detail. Live calls load first, because every other store is then loaded for those calls — a bounded read rather than a full table scan, which is why none of these stores needs a "load everything" method at all.

#stepwhy it is not bookkeeping
1live callsbounds everything after it; a closed call is history, and history is answered with SQL
2assignmentsrebuilds the set of agents who already declined — without it the matcher offers the same caller to the same silent desk forever
3attestationsrestores the count that re-locks the identity control; an empty history would silently unlock a settled question
4captures, wrap-ups, last decisionthe offer card renders the matcher's rationale, and a restored offer with no explanation is the one screen here that cannot say why it is showing you something
5the waiting poolcomputed from the calls themselves — not read from anywhere
6presencelast, because it is a projection of a log rather than a reload of rows

Step 2 is the one that looks like housekeeping and is not. Forget it and every individual decision the matcher makes stays perfectly defensible while the caller watches one agent fail to answer, indefinitely.

06 — the exceptionThe digits we refuse to keep

Everywhere else in this codebase, the safe move is to record what happened. Keypad capture inverts that, and the reason is that capture is untyped: the agent starts it, the caller keys whatever they happen to be holding, the agent stops it. Nobody has said what the digits are.

So until something identifies them, they could be a policy number, a national ID, or a card number — and an unidentified number is treated as sensitive:

always writtenwritten only once named
masked = ••••••0811
digit_count = 10
every lookup and its outcome		 digits = 2024000811

"Named" means a lookup matched, or the agent labelled it — at which point the digits are a policy or claim number, which is not a secret and is worth having on the record. The consequence is deliberate: a restart mid-capture returns the fact that a capture happened and how long it was, never the value. The retention policy asks for short-lived and one-click-discardable, and a durable copy of an unknown number is the opposite of both.

a different question from the disclosure gate

Masking protects the log, never the agent. These are the caller's own keystrokes, typed seconds ago, to the person they are speaking to — an earlier version hid them from the agent who had just asked for them, which deleted the feature and protected nobody.

07 — the proofEnding a process on purpose

Each store has round-trip tests. Those are necessary and not sufficient: a previous bug in this project was three services that were individually correct and called by nothing at all. Per-component tests passed the whole time.

So the real test boots an app, works through the actual HTTP API, throws the app away, boots a second one on the same storage, and asks it what it knows. The only thing crossing that boundary is the database — no shared objects, nothing that could answer from a cache it happens to still be holding.

Then re-checked outside the test framework, because a test client is still one Python process: two real server processes against a real database, the first one killed mid-shift. 

PASS  the call itself came back
PASS  the attested identity came back
PASS  last_call did NOT carry across
PASS  the brief still renders
PASS  the Thai summary is identical

08 — the bugsTwo things this found, neither about databases

A column nobody ever wrote to

CallSession.identity had existed since the first phase. Nothing ever populated it — the live value lived only in a dictionary. So a restored call had no identity, so the brief renderer returned nothing, so the agent's screen was blank on a call they were in the middle of. The column was right, the model was right, and the write was simply absent. Findable only by restarting and looking.

An entire package that was never committed

B9

The .gitignore contained models/, under a heading meaning machine-learning weights. A gitignore pattern with no internal slash matches a directory of that name at any depth — so it also matched src/readycall/db/models/, and the entire database model package was never committed. The previous phase looked completely landed. A fresh clone had no tables at all.

Every check this project runs — tests, type checking, linting, the migration, the live database verification — reads the working tree. Not one of them is a statement about what the repository actually contains.

Both belong to a family this project keeps meeting: a confident, plausible, wrong result that nobody looked at. A timer that measured zero. A matcher that said "nobody is qualified" directly above a qualified agent. Three services with no driver. A clock correction that cancelled itself out.

When something looks fine, check that it is actually running — and now, that it is actually committed.
