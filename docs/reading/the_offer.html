The thirty seconds after the menu

The caller has pressed their way to the right queue. Nobody has answered yet. This is what the system does with that gap — and why the most important thing about it is that it cannot change where the call goes.

HACK VIDVA 2026-08-31 decisions D88 · D89 · D90

01The one-paragraph version

Before this, the call went: menu → queue → wait silently → an agent answers. Now it goes: menu → queue → “please hold” → “would you like to describe your problem while you wait?” → they say yes, no, or nothing → an agent answers.

That is the entire feature. What took the work was making sure the middle part cannot break the beginning.

02Why there is a line drawn across the call

The pitch says the AI reads the customer's problem before the agent picks up. The risk hiding in that promise is obvious once you say it out loud: if the AI is what works out why someone is calling, then a caller who says nothing — or whose speech recognition fails — reaches nobody useful. The system would be worse than the keypad menu every call centre in Thailand already has.

So the design splits the call in half, and the split is load-bearing:

Because that line matters so much, the new code is a separate machine in a separate folder, not two more states bolted onto the menu. The menu decides where the call goes. This decides how much the agent knows when it gets there. Put them in one file and the first person to write if caller_declined: route_differently() finds nothing standing in the way.

the test that guards it

Three callers — one records, one refuses, one ignores the question entirely — all land in q_health_policy. If that assertion ever fails, the AI has started deciding where calls go, and the whole product thesis has quietly inverted.

03What the caller actually hears now

All of it is real, pre-rendered Thai from one YAML file — no studio, no live synthesis, works with no internet:

กรุณาถือสายรอสักครู่ค่ะ
   “Please hold for a moment.”

ระหว่างรอสาย ท่านสามารถเล่าเรื่องที่ต้องการติดต่อไว้ล่วงหน้าได้
เจ้าหน้าที่จะเห็นข้อมูลทันทีที่รับสาย
กด 1 เพื่อบันทึกข้อความ   กด 2 เพื่อรอสายตามปกติ
   “While you wait, you can describe what you're calling about.
    The agent will see it the moment they answer.
    Press 1 to record a message, press 2 to keep holding.”

No position, and no estimated wait. That took two goes to get right.

The first version said “you are number three, about two minutes.” Then “you are number three”, on the reasoning that we can count a queue exactly even though we cannot predict how long it drains.

Both were wrong, because there is no line to have a position in. The matcher builds a full caller × agent matrix and re-solves it every tick. Arrival order is not an input anywhere. What the code was actually computing was the size of the pool when you arrived — and then saying it out loud as though it were a place in a queue.

Here is the real scoring code on three callers, one queue, one free agent:

caller                                      urgency    fit    score
arrived 1st, waited 200s, routine             3.000  0.650    1.950
arrived 2nd, waited  90s, routine             2.050  0.650    1.333
arrived 3rd, waited   0s, EMERGENCY           2.200  1.050    2.310  <- answered first

Give all three the same fit and the 200-second waiter wins instead — waiting pushes urgency to its ceiling and beats an emergency on its own. Both overtakes are the design working correctly, and both make an announced number a promise the system breaks. Worse, it breaks it most often for low-urgency callers — the patient ones, most likely to have believed it.

So the caller now hears “กรุณาถือสายรอสักครู่ค่ะ” and nothing else. The lesson is small and sharp: we can count a pool is not we can rank it.

Why the last two are different rows and not one

“They said no” and “we never asked” are different facts about a human being. If both produced an empty consent list, an agent staring at a thin brief would have no way to tell them apart — and the right behaviour differs: the first means don't raise it, the second means you may.

Storing a refusal costs one row. Not storing it costs the agent the ability to be appropriate.

05The bit that is genuinely hard: the recording outlives the request

Here is the dilemma. An agent frees up while the caller is mid-sentence. Cut them off, or make the agent wait? Both answers are bad, and the second one breaks the product's core promise — nobody waits longer because of our AI.

The resolution is that the grace period was already there. An agent spends five to fifteen seconds reading the brief before pressing Accept. Those seconds are seconds the caller can still be talking.

This is also why the code looks unfinished and is not. The function that makes the offer returns the moment the caller answers and leaves the recording running. It has to: the three things that actually end a recording — a detected silence, the maximum length, and that Accept press — all arrive from somewhere else, and the last one arrives seconds later, from a different person, on a different connection.

Proved on a real running server rather than argued about in a test:

intake started    call_01M1C7KX…   strategy=passive
hold settled      … outcome=waiting  recording=True     ← offer out, still talking
intake finalized  … partial=True  reason=offer_accepted ← the agent pressed Accept
hold settled      … outcome=cut_short recording=False

06Two things I got wrong

wrong · caught by a fake caller

The first version kept looping until the recording finished. A scripted test caller exposed it immediately: press 1, run out of script, and the loop “hears” a silence that never happened and closes the recording.

The real fault was bigger than the bug. Finishing that loop meant this file owning a media layer that does not exist yet — and therefore inventing what it would report. This project has been bitten four separate times by confident, plausible, wrong results that no test could see. That is the same shape.

wrong · found while moving the repeat key

A prompt was spelling out a value that lives in config. The apology line said “…กด 9 เพื่อฟังตัวเลือกอีกครั้ง” as literal Thai text, while menus.yaml separately owned the key the system actually honoured.

Change the key and the apology would go on naming a button that did nothing — and nothing would have failed. The guard that checks prompts only checks that ids resolve and that declared slots are used. A hardcoded digit is neither.

It is a proper {repeat_key} slot now, and the test asserts the rendered line rather than the template, so the two cannot drift apart again.

07And the change you just asked for: repeat moves to 0

Last session we removed the operator key, and that decision admitted exactly one cost: a caller who pressed 0 out of habit heard an apology for a button that did nothing. Meanwhile repeat was sitting on 9, where an earlier decision had put it — and that decision had explicitly rejected this move:

Rejected: moving repeat onto 0. It only becomes free if the operator key goes, and 9-repeats / 0-operator is the pairing callers already have muscle memory for.

Both halves of that are now void. The operator key did go, so 0 is free — and the muscle-memory claim is the one you already demolished: people call their insurer once or twice a year, which is nowhere near enough repetition for a reflex.

What is left is a better argument than “the key was spare”. 0 is where a lost caller's thumb already goes — not from a reflex for our menu, but from the cross-service convention that 0 means “I need a person”. That instinct is real even when the reflex is not, and it fires precisely when someone is confused, which is exactly when hearing the options again helps most. It is also bottom-centre and alone on its row, findable by touch by someone holding a phone to their ear.

So the old habit now buys something useful. Press 0 expecting an operator and you get the menu read out again, instead of an apology. The one cost that removing the operator admitted to is deleted.

Nothing else moved: still no operator, still no limit on wrong presses, still exactly one reserved key, and the way out of a menu is still its own spoken “เรื่องอื่นๆ” option.

08What the recording is allowed to change

It can change who answers and how soon. It can never change which queue.

That boundary is now written down (D92), because it was implied and never stated — and the code that could break it hasn't been written yet, which is the right moment to fix a rule.

Decided byWhat it setsCan speech move it?
the keypadqueue_id, required_skillNo. Frozen once the menu ends
the keypad, refined by speechintent_urgencyYes — how soon, relative to others on the same queue
context and historythe fit signalsYes — which agent, within the queue

The reason is the worst case. Under this rule a mis-transcription costs the caller a slightly less ideal agent on the right queue. Without it, the least reliable component in the system gets to move them off the right queue entirely — and the keypress is the one piece of intent the caller deliberately gave us.

A caller genuinely in the wrong queue is a transfer, done by a human who has actually spoken to them. Re-routing should have a person attached.

Today none of it is wired anyway. Every matcher input traces back to the menu; the transcript reaches the agent's screen and nothing else.

09What is still missing

The audio. All of it.

There is no media gateway, no voice-activity detection, no speech-to-text worker, and no encrypted recording. The socket they plug into is real and tested — IntakeService.on_turn(call_id, turn) — and today the only things that call it are the test suite and the scenario runner.

That is the next stretch, and it is the only part of this whole project with hardware risk: a Thai Whisper model on an RTX 3050. Step zero is a multi-gigabyte dependency install, which is why it has not happened yet.

One question is genuinely open and needs answering before the analysis work starts: a caller on the health line will speak health data into a recording, and under the PDPA that is a separately-consented category which nothing currently asks for.
