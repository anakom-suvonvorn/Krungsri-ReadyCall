D135 · the planned item that went sideways

The sentence about what the bank already knew

What it is

When a broker answers a call, one panel says “ข้อมูลอื่นๆ ที่มีเกี่ยวกับลูกค้า” — everything the bank already holds about this person that the broker would otherwise have to ask for. Home loan, new child, deposits, past conversations. That panel was built the day before (D134) and shipped with a note saying its facts were verified on a running server but its model-written sentence had never been seen working.

Where

The facts come from services/brief/context_facts.py. The sentence is written by ContextSummariser in services/analysis/summary.py, using a prompt file at prompts/th/summarize_context.*.md. It renders in the workstation's brief.

Why it needed doing first

Two guards could have been eating the sentence. One refuses any run of four or more digits, because a coverage amount must never be written by a model — and this project prints dates in the Buddhist era, so 30/08/2565 looks exactly like money. That had already thrown away one correct summary.

How it was checked, and what actually turned up

I ran the real summariser over the real customer's facts six times against a live model and read every sentence. The guards were fine — sixteen clean runs, zero refusals, Buddhist dates in every one. The prompt was not:

Over six live runsv1 (old)v2 (shipped)
Answered / refused5 / 16 / 0
Led with a life event (the “why now”)0 of 56 of 6
Named the mortgage4 of 56 of 6
Claimed something was “not found”1 of 50 of 6

The old prompt told the model to lead with whatever relates to today's call. The panel's own ordering rule says the opposite, and says why: life events come first because they are the only thing there that answers “why now”, and the only thing the broker could not have guessed from the policy list already in front of them. The prompt and the ordering disagreed, and the prompt won on every single call.

So the sentence a judge would read opened with “they once rang about renewing a motor policy, and it's closed” — while the mortgage and the new child, which the orientation deck calls the cleanest example of right customer × right time in the whole brief, came last or not at all.

⚠️ The near-miss worth remembering

My first rewrite fixed all three problems and was green on every counter — and it recited the customer's balance bands (1m-5m, 500k-1m) in 6 of 6 runs, where the old one never had. The money guard cannot see those: there is no run of four digits in 1m-5m.

Only reading the Thai caught it. That is now written into the project's landmine list as one line: a green counter is not a read output.

What ships is a new file, summarize_context.v2.md. The old one stays on disk on purpose — every stored summary records which prompt file produced it, so deleting v1 would make old results unexplainable.

D136 · packaging

The container that starts anywhere

What it is

Two commands and you have a running ReadyCall, with no uv, no Node, no Python installed: 

docker build -t readycall .
docker run --rm -p 8000:8000 readycall

Then /sim and /workstation on port 8000. There is also a compose profile — --profile demo — kept behind a profile so every Postgres/MinIO command that worked before still does exactly what it did.

Why, and why it ships without the speech engine

The plan's own risk register has one rule about venues: never depend on one. But a plain container cannot reach the GPU without host setup that varies by machine — which is precisely what fails on the day. So the image ships on the scripted speech engine, and the real Typhoon engine runs on our own laptop for the pitch and the recorded video. Everything else in it is real.

How it was verified — and the three faults that found

By running the container and driving it, not by watching the build succeed:

  1. /sim and the customer's paired screen returned 404 — silently. The app mounts those two pages only if their folder exists, which is right for a developer's clone and means an image missing them starts, reports healthy, serves the workstation, and loses two of the three customer screens with no error anywhere. The first build did exactly that. Found by fetching /sim.
  2. The Postgres profile used an environment variable nothing reads. DATABASE_URL looks obvious; the setting is actually READYCALL_DATABASE_URL behind a computed property, so the app would have quietly talked to itself instead of the database.
  3. A rebuild took 484 seconds. One line was changing ownership of ~4,000 files. Creating the user before anything is written took it to 44 seconds — on a feature-freeze day that is the difference between iterating and not.

The whole AI story runs in the container with no audio at all. That is what the typed intake bought. Verified inside the image: three Thai sentences typed into /sim reached the broker's transcript panel, a fast model's summary of them was on the offer card before Accept, the careful model replaced it after, and the context panel carried its own sentence. Every .wav is excluded from the image — there is no audio in it and none is needed.

D137 · the last piece of compare-and-best-fit

A model writes the reason, and never the ranking

What it is

In the plan panel, each compared plan has a sentence under it saying how it differs from what the customer holds. That sentence used to be assembled by code — honest, traceable, and dull: it named the single biggest improvement and the single biggest downside and stopped. A model writes it now.

Why the split is where it is

The order of those plans is arithmetic over weights in a config file, computed from real coverage figures. That is deliberate: a model that ranks is a model that can be argued into putting a plan first. A model that explains an ordering it never saw a score for cannot. So the model rewrites one string and touches nothing else — the service that does the ranking does not know this feature exists.

What it produces

On the demo data, the plan that has the better figure in three of four rows and still ranks second:

เพิ่มค่าห้องและค่าอาหารจาก 3,000 เป็น 6,000 วงเงินผู้ป่วยในต่อปีจาก 1,000,000 เป็น 10,000,000 และค่ารักษาผู้ป่วยนอกจาก 1,500 เป็น 2,500 แต่ค่าใช้จ่ายส่วนแรกสูงขึ้นจาก 0 เป็น 30,000

The ฿30,000 deductible is exactly why it ranks second, and the sentence says so. The old generated one mentioned two of those four differences.

The four guards

  1. Every number it writes must be one we handed it. Not “no numbers” — the useful sentence quotes real amounts, and that is what makes it a comparison rather than an adjective. So the check is provenance: a figure the model produced that was not in its input is a coverage amount invented by a model, and it is refused.
  2. It may not rank. No “best”, “most suitable”, “you should pick”.
  3. It may not mention price. There is no premium anywhere in its input, so any price is invented by construction.
  4. It may not promise cover. Underwriting belongs to the insurer.

A refused sentence falls back to the generated one, so none of this can break the table.

⚠️ Changed on 10 September (D148). What follows is no longer true: waiting for the model froze the line selector for ~2.4 s on every switch. The panel now answers in about 6 ms with the generated sentences and fills the model's in when they land.

This is the one model call in the system that is waited for, and the reason is mechanical: the plan panel is fetched once when you open it and never polled, so a background task would finish into a screen nothing refreshes. It is bounded at 3 seconds, it is nowhere near the call path, and the ranked table is already computed when the wait starts. Measured: 2.4 s the first time, 4 ms after that from a cache.

A small AI chip marks a sentence a model wrote. It is absent, rather than saying “generated”, when no model wrote it — a badge on every row stops being information.

Two faults surfaced on the first live run, and neither was a guard. The startup warm-up — which exists to pay the first hosted call's cost so no caller does — was running on a 4-second deadline, and a cold call plus the OpenAI parameter negotiation takes longer than that. So it timed out, the negotiation went unpaid, and the next real call failed outright. And my own cache stored that failure permanently. Both fixed; the cache now tells a refusal (deterministic, worth caching) apart from a failed call (transient, never cached).

B41 · the one you found

The screen said “no model configured”. It was calling one.

You asked why the line in the custom test-call dialog could never be ticked:

ให้โมเดลสรุป — ยังไม่ได้ตั้งค่าโมเดล — จะใช้สรุปแบบกฎ ซึ่งไม่เรียกโมเดลใดๆ

Two answers. The first: that line is a status report, not a control — the dialog is built to describe what the machine is, not to configure it. The second is the problem: the sentence was false on your machine.

What was actually happening

There are two model clients, not one. A “careful” one for the full summary after Accept, and a “fast” one for anything that has to arrive while somebody is waiting. The fast one is built whenever LLM_FAST_MODEL is set — whatever LLM_PROVIDER says. And three of the four AI features run on the fast client:

  • the summary that lands on the offer card before you press Accept;
  • the customer-context panel (the one from D135 above);
  • the comparison's reason sentence (D137 above).

Your .env said, in effect:

LLM_PROVIDER=rulebased          # → the dialog concluded "no model"
LLM_FAST_PROVIDER=openai_compatible
LLM_FAST_MODEL=gpt-5.4-mini     # → but this built a REAL client

So the machine was calling gpt-5.4-mini at OpenAI three times per call, and being billed for it, while the screen said it called nothing. The dialog computed “is the AI on?” from the main provider alone.

How it was proved

Not by argument — by construction, and then on a running server: 

LLM_PROVIDER in .env : rulebased
main client          : rulebased / rulebased-v1
fast client          : openai_compatible / gpt-5.4-mini

And a call placed on that “rule-based” instance logged context summary unavailable error= — an empty error, which is a bare timeout, which the rule-based adapter can never produce because it does no network I/O at all.

The fix, in three parts

  1. The dialog asks the running system what was built, not the config file.
  2. It names the two stages apart, because they genuinely differ. One combined sentence is exactly what hid this.
  3. The startup warm-up had the same wrong test, so on your configuration the real fast client was never warmed and its first call timed out cold. That is why the context panel sometimes appeared to do nothing on the first call of a session.

The lesson, written into the docs

A status line is a claim, and a claim derived from one field is a claim about that field, not about the system. This project's most repeated fault is code that runs and nothing calls it. This is the mirror image: code that is called, and the screen says it is not — which is worse, because nothing fails and somebody plans a demo around it.

D138 · the thing you asked for

The ⚙ panel

How to use it

There is a ⚙ button in the workstation header, next to ออกจากระบบ. It opens a panel with three choices:

  • ปิดโมเดล — ใช้สรุปแบบกฎ — the AI off, entirely.
  • Anthropic · claude-sonnet-5
  • OpenAI-compatible · gpt-5.4-mini

One click switches. No restart. A choice you have no key for is greyed out and says which key is missing. Underneath, the panel reports the two stages separately — so you can see at a glance that, say, the full summary is rule-based while the preview is a real model.

It is not saved. Restart and it returns to whatever .env says. That is deliberate: a switch thrown for a demo that silently outlives the demo is a setting nobody can find later.

Why this is worth a button

The strongest thing this system can show in five minutes is the same call, twice — once with the model off, so the arithmetic ranking and the rule-based brief stand up on their own, and once with it on. Before this, that meant editing a file and restarting mid-pitch.

The five rules behind it, because a settings endpoint is a good place for a hole

  1. The request names a provider and nothing else. No key, no URL, no model id. A request that could name its own endpoint would let anyone signed in point our summariser at a server of their choosing — and post every caller's words to it. A test sends those fields and asserts they are rejected.
  2. No key ever reaches the browser. “Available” is a yes/no the server worked out from its own environment.
  3. Clients are built by the one factory that builds them at startup, so the switch cannot drift from the boot path.
  4. The config object stays frozen. The switch copies it; nothing else in the process starts reading different settings than it booted with.
  5. The whole thing is a 404 on a non-demo instance, behind the same flag that allows signing in as any agent.

Two things it must do that are easy to miss

Turning the model off turns the fast one off too — otherwise the offer card keeps calling a hosted model while the panel says the AI is disabled, which is B41 recreated by the control built to fix it. And both text caches are cleared, or you would see one model's prose on a screen reporting the other.
