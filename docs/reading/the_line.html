The Line

Every other page in this project describes something you can look at. This one describes what the caller hears — so here it is as a phone you can actually press.

The keypad menu is not a preamble to the interesting part. It is the part that decides where the call goes, and it does that before a single word is transcribed. The AI runs afterwards, while the caller waits, and adds the detail a keypad cannot capture — which hospital, which plate, how urgent. If the AI fails, the routing is unaffected, because routing was never its job.

That is D37, and it sets the bar for this page: not "the AI works" but parity with an ordinary call centre. Everything below is about the awkward cases, because that is where parity is won or lost.

Three things are worth trying before reading on. Press 8 three times and watch where you end up — it is a queue, not a dial tone. Press 9 five times and watch the attempt counter refuse to move. And switch the caller to recognised, then press 4 for health: the key you press and the key that gets recorded are different, and the panel shows both.

01Every sentence is text in one file

Nothing you just heard was recorded by a person, and nothing was synthesised while the call was running. config/voice_prompts.yaml holds 32 prompts as Thai text; scripts/build_prompts.py renders each one to a clip at build time; the call plays a file. That is D24, and the two things it rules out are the point:

RejectedBecause
hand-recorded audio changing one word costs a studio booking — and wording is exactly what gets tuned the night before
synthesis during the call latency, cost, and a network dependency standing between a caller and a menu, on a venue's wifi

The cache key is hash(text, voice, engine) — the rendered text, not the prompt id. That one choice does two jobs. Editing a single Thai line re-renders exactly that line and reuses the other 62, which was measured rather than assumed. And two prompts that say the same words become one clip.

The honest limit. TTS_ENGINE defaults to null, which records what it was asked to say and synthesises nothing. So today the pack is a manifest, not audio — which is also why this page shows you the words rather than playing them. A real voice is a config change and a re-run, and it should be chosen on a listening test of these actual 63 lines rather than a vendor's spec sheet.

02A menu cannot be one clip

Here is the collision that only appears once you build it. D24 says every line is a pre-rendered file. D37 says a recognised caller hears their likely options first. Both cannot be true of one baked recording of "กด 1 ประกันรถยนต์ กด 2 ประกันสุขภาพ …" — the order changes per caller.

So a menu is composed from clips that were all pre-rendered: a lead-in, one line per option, then the reserved-key hint. Composition is playback, not synthesis, so D24 holds exactly as written. That is D80.

    recognised — open travel claim, life policy

      The rejected alternative sounds cheaper than it is: one clip per menu per ordering. The product-line menu has five options, so 120 orderings, and every wording edit multiplies through all of them.

      What composition bought, beyond making the feature possible at all:

      • the label exists in exactly one file. voice_prompts.yaml contains no menu options; the build reads them from menus.yaml — the same file that does the routing. There is no second copy of ประกันสุขภาพ to drift.
      • the same words are one clip. ติดตามสถานะเคลม is key 3 in both the motor and the health menu, so it renders once. 32 prompts and 32 menu options come to 63 clips.

      That dedupe is not a footnote about disk space. It is the same mechanism that makes a dynamic line cacheable at all: everyone who is third in the queue hears the same file, so the pack warms up in minutes rather than never.

      03What they pressed is not what gets stored

      Follow the promotion through. Travel is promoted, so it takes key 1. The caller presses 1. CallSession.menu_path records keypresses. The stored path now says 1, which in menus.yaml means motor.

      Nothing fails. The call is routed correctly, because routing used the live presentation. But the record is wrong, and everything reading it later — the brief, the intent source shown to the agent, a replayed scenario, an auditor asking what the caller chose — is quietly wrong with it. This is the family of bug this project keeps meeting: a confident, plausible, wrong result that nothing is in a position to notice.

      D81 fixes it at the only moment the answer is unambiguous. The press is resolved to its canonical option the instant it arrives. menu_path always holds keys as menus.yaml spells them; the raw presses are kept separately, where they are a UX signal — a confused menu path is worth seeing — rather than routing evidence. 

      presentation.resolve("4")   # spoken 4 -> canonical 2 -> health
menu_path      = ("2", "4")   # canonical, on every call
outcome.pressed = ("4", "4")  # what actually happened under their thumb

      The rule reaches into the test suite too. ScriptedChoices — used by every scenario file — takes canonical keys and looks up whichever key is actually under that option. A scenario keeps meaning what it says when a menu is reordered, instead of silently pressing the wrong thing. Without that, every scenario involving a recognised caller becomes a trap that springs the day somebody tunes the personalisation weights.

      And the reason for renumbering rather than merely shuffling: "กด 3 … กด 1 … กด 2" makes the caller do the sorting. If the order changes, the numbers change with it.

      One thing the machine refuses to claim

      A published number may assume an intent — someone dialling the number printed in their glovebox is very likely standing beside a damaged car. That is real evidence and it picks the queue. But it is weaker than a keypress, so the two are kept apart: the outcome's intent holds only what was pressed, while the result carries the best available answer with a source saying whether it came from dtmf, the app, the did, or nothing at all. The agent's brief has to be able to tell "they told us" from "we assumed". Try it: dial the motor-claims number and say nothing.

      05Why the rules live in a machine with no I/O

      begin / on_digit / on_timeout / on_hangup, each returning what to play next. A thin async driver plays it and holds no rules at all — which is why this page could be built from the same shape.

      That is a direct consequence of B7. An IVR written as a coroutine awaiting DTMF can only be tested by feeding it a fake phone line, and the rungs that fire because time passed are then exactly the ones that end up driven by nothing. Which is what B7 was: three services, all written, all correct, all called by nothing. Here silence is a method call. 

      first  = machine.on_timeout(run)   # re-prompt once
second = machine.on_timeout(run)   # -> EXHAUSTED, reason="silence_x2"

      06What is not built

      Everything above the queue line. Below it — the press-1/press-2 intake offer, the recording, the media gateway, VAD endpointing, the STT worker and the bake-off on the RTX 3050 — is step four of this phase and has not started. The prompts for all of it are already written, rendered and mapped to roles; they are text waiting for the machinery that plays them.

      The identify step that reaches assurance L3 by keypad, and the post-call rating keypress, are in the same position: the sentences exist, nothing calls them yet.
